Do not select old `78e309d` merely because its artifact is listed. |
| Pool timeouts or concurrent asset/metadata 503s recur | Confirm the deployed source includes the `6527ba8` early session-release fix and the wait is fifteen seconds. | Reader connection or readiness fails | Preserve destination data. Check exact-project session endpoint, TLS, DNS, private credential, role membership/policies and pool/query limits. Readiness must fail before the listener opens. Merge a corrected reviewed setting and redeploy the intended guarded commit; never switch back to the expired source or use an owner credential. |
| Reader credential is compromised | Rotate only the independent login's private credential through the reviewed verifier-only process; update its service secret through a merge. If needed, disable that login and close only its affected sessions under a reviewed incident action. Preserve unrelated roles, data and authentication secrets. |
| Authentication or public authorization regresses | Check preserved JWT/session behavior, the public publication guards, HTTP read-only gate and scoped role/policies. Restore only the reviewed narrow configuration. Do not broadly disable RLS, grant browser roles backend-table access, or expose service credentials. Editing, publishing and feedback remain paused. |
| Manifest or published assets fail | Distinguish database readiness, current GCU v5 metadata, Storage availability and cache recovery. Keep the current publication/version references unchanged; restore access to authentic existing objects or use a verified compatible application build. Do not publish local v1 data over v5 or fabricate records. |
| ArcGIS/Matterport or mobile UI regresses | Compare deployed commit and asset hashes, SDK/origin/network failures, map/browser capabilities, public payloads and actual screenshots. Confirm `20261113viewmode2` and translated view-mode behavior after DOM translation. Restore only a compatible guarded viewer build/configuration; `a787124` has the known label defect. A frontend failure is not permission to roll back occupied database contents. |
| Missing/conflicting source records are discovered | Preserve destination records and quarantined source copies. Resolve business identity, foreign keys and asset/version provenance in staging. There is no automatic production merge or overwrite command in the recovery tooling. |
| A future merge fails | Roll back only its open transaction, or stop at documented checkpoints and review narrow compensation. The executed read-only release performed no source-data merge and requires no database data rollback. Do not delete rows merely because an exported source uses their IDs. |
| Destination data corruption is independently confirmed | Restore the verified backup into a fresh isolated matching environment, compare changes since capture and prepare selective reviewed recovery. The additive reader roles and policies do not require a destructive rollback when an application deployment fails. Keep their audit history; disable or rotate the independent login only when warranted. No table/schema/database reset, blanket grant removal, role-owner replacement or clean restore is authorized by this plan.

## Verification after recovery

For any deployment/configuration recovery, record the new deployment ID and exact commit, secret-free key changes, verified native role/TLS/read-only state, migration-disabled/readiness-passed/listener startup order, health/manifest HTTP results, GCU v5/five-floor scope, expected 99 curated POIs, public/private authorization and actual desktop/mobile rendering/search/routing screenshots. Include a bounded concurrent bundle/metadata read burst and view-mode checks after translation; initial serialized HTTP 200 responses did not reveal the first release's defects. Verify that editing/publishing/feedback stay paused and that no source-derived application DML occurred. Attribute errors by deployment time so pre-16:25:56 UTC failures are not presented as final-release failures or silently erased.

A normal redeploy is required to apply pending configuration; do not assume a restart applies newly saved variables. Render rollback behavior can change auto-deploy settings or use configuration tied to a retained artifact. Inspect the resulting commit and effective safe flags rather than assuming the live reader configuration was restored. No rollback is successful solely because a previous container starts or a TCP check passes.

Forbidden recovery shortcuts remain: destructive resets, truncation/schema drops, clean restores against occupied Supabase, blind conflict updates, database replacement, and use of the suspended source as a healthy fallback. Do not run the legacy `platform/scripts/restore.sh` against production.

Reference: [Render rollback behavior and limitations](https://render.com/docs/rollbacks).
